# Правила разработки сайта «Азбука Потолков»

> Этот документ фиксирует утверждённый технологический подход. Следовать ему при проектировании и разработке, если пользователь явно не изменил отдельное решение более новым указанием.

## 1. Основные приоритеты

Кодовая база должна быть:

- простой и соразмерной небольшому сайту;
- современной и предсказуемой;
- понятной без предварительного изучения сложной архитектуры;
- удобной для продолжения работы другим разработчиком или ИИ;
- построенной на известных, стабильных и хорошо документированных технологиях;
- свободной от зависимостей и абстракций без реальной пользы для проекта.

Не проектировать сайт как крупный сервис и не создавать расширяемость ради гипотетического будущего.

## 2. Утверждённый стек

### Основа

- Next.js с App Router.
- React.
- TypeScript в строгом режиме (`strict: true`).
- npm как менеджер пакетов.

Next.js используется преимущественно для статических публичных страниц, маршрутизации, SEO-метаданных, изображений и шрифтов. Наличие Next.js не означает необходимость backend или динамического серверного рендеринга.

### Стили

- Обычный современный CSS.
- CSS Modules для стилей компонентов и секций.
- Один глобальный файл для reset, дизайн-токенов, базовой типографики и действительно общих правил.
- CSS custom properties для цветов, отступов, размеров контейнера, типографики и других повторяющихся значений.

Не использовать Tailwind и Sass/SCSS без нового явного требования или доказанной необходимости.

### Анимации

- Пакет `motion` входит в базовый стек.
- React API импортируется из `motion/react`.
- Простые hover-, focus-эффекты и автономные переходы выполнять через CSS.
- Motion использовать для появления элементов при прокрутке, stagger-анимаций, scroll-linked эффектов, layout-переходов и другой координируемой анимации.
- Общие варианты, длительности и easing централизовать в небольшом анимационном слое.
- Не размазывать одинаковые конфигурации Motion по секциям.
- Не превращать статичные страницы или крупные секции в Client Components только ради одного эффекта. Использовать небольшие клиентские обёртки.
- Всегда учитывать `prefers-reduced-motion`; анимация не должна быть необходима для понимания контента или навигации.
- Не добавлять GSAP без отдельной подтверждённой задачи, которую Motion и CSS не решают разумно.

### Формы

- Использовать семантический HTML `<form>` и нативные поля.
- Базовая клиентская проверка: `required`, корректные типы полей, `minLength`, `autoComplete` и понятные сообщения.
- Для отправки использовать `FormData` и небольшой изолированный адаптер.
- Поддерживать ясные состояния: исходное, отправка, успех, ошибка.
- Способ отправки будет определён позднее: почта, Telegram, CRM или внешний endpoint.
- Не создавать backend до появления реальной необходимости и утверждённого способа отправки.

React Hook Form и Zod не устанавливать на старте. React Hook Form допустим при появлении многошаговой или динамической формы. Zod допустим при появлении собственного API или другого runtime-контракта с недоверенными данными.

### Изображения

- Использовать `next/image`.
- Изображения организовывать по назначению и проектам, с понятными именами файлов.
- Всегда указывать корректный `alt`; декоративным изображениям задавать пустой `alt`.
- Задавать корректные размеры и `sizes`, предотвращать layout shift.
- Hero/LCP-изображение загружать приоритетно; остальные — лениво, если это уместно.
- Не помещать в публичную сборку неподготовленные тяжёлые исходники.
- Не добавлять сторонний image CDN или отдельную медиасистему без необходимости.

#### Подготовка фотографий

Фотография объекта — часть продукта, а не служебный ассет. Экономия веса не может идти в ущерб её качеству.

- Разрешение исходника считать от максимального размера показа с учётом плотности пикселей (×2), а не подбирать на глаз. Отдельно проверять лайтбокс и другие полноэкранные просмотры: там кадр крупнее, чем в сетке превью.
- Фотографии проектов готовить в webp без даунскейла: сохранять исходное разрешение съёмки. Текущий ориентир — 3600 px по длинной стороне, `quality: 94`.
- Учитывать двойное сжатие: `next/image` пережимает подготовленный файл ещё раз, по умолчанию с `quality: 75`. Фотографиям, которые показываются крупно, задавать `quality={95}` и держать разрешённые значения в `images.qualities` в `next.config.ts`. Мелким превью значения по умолчанию достаточно.
- Исходники со съёмки хранить вне `public/` — например, в `projects/<раздел>/<номер>/`. В сборку класть только подготовленные файлы.
- Не понижать разрешение и качество фотографий ради размера репозитория. Несколько лишних мегабайт дешевле, чем мыло в портфолио; если вес действительно мешает, сначала согласовать компромисс с пользователем и показать замеры.

### Шрифты

- Использовать `next/font/local` и WOFF2 после утверждения гарнитуры.
- Предпочитать одну variable-гарнитуру или минимальный набор реально используемых начертаний.
- Подключать шрифт централизованно в корневом layout.
- Если выбран Google Font, допустим `next/font/google`, который размещает шрифт локально в сборке.
- Не устанавливать отдельные npm-пакеты шрифтов без необходимости.

### Иконки

- Для небольшого числа иконок использовать собственные SVG-компоненты или SVG-файлы.
- Использовать `currentColor`, корректные `aria-label` или `aria-hidden`.
- Не устанавливать библиотеку иконок ради нескольких стрелок и контактных символов.
- `lucide-react` допустим только при появлении заметного набора стандартных интерфейсных иконок.

### UI

- Не использовать готовую UI-библиотеку.
- Создавать только необходимые проекту примитивы: например, Button, Container, SectionHeading, ProjectCard, FormField.
- Не подключать MUI, Ant Design, Chakra UI, shadcn/ui или Radix без конкретной задачи, оправдывающей зависимость.
- Для сложного доступного компонента вроде dialog допустима точечная headless-зависимость после оценки необходимости.

### Условные классы

- `clsx` не устанавливать автоматически.
- Для одного-двух условий использовать простой и читаемый вариант средствами языка.
- Добавить `clsx` можно, если появится несколько компонентов с большим количеством вариантов и условных состояний.
- Не создавать функцию `cn()` без фактической необходимости.

## 3. Архитектура и применимые идеи FSD

Полный Feature-Sliced Design в проекте не используется. Для контентного сайта с небольшим числом интерактивных сценариев слои `widgets`, `features` и `entities`, публичные API каждого слайса и строгая FSD-декомпозиция создадут лишнюю вложенность и споры о классификации.

Также учитывать, что имена `app` и `pages` имеют специальное значение в Next.js, поэтому буквальное наложение FSD на App Router ухудшит ясность структуры.

### Принципы FSD, которые нужно применять

- Группировать связанный код рядом.
- Называть модули по назначению и понятному бизнес-смыслу.
- Разделять композицию страницы, крупные секции и универсальные UI-примитивы.
- Держать зависимости направленными от конкретного к общему: страницы используют секции, секции используют UI-примитивы, но не наоборот.
- Не допускать циклических импортов.
- Не выносить код в общий слой до появления реального повторного использования.
- Хранить локальные состояния, стили, типы и вспомогательную логику рядом с модулем, которому они принадлежат.
- Не превращать `lib`, `types`, `hooks` или `utils` в свалку несвязанных файлов.
- Оптимизировать структуру для быстрого поиска кода новым разработчиком или ИИ.

Эту организацию не называть FSD: это простая структура, использующая отдельные полезные принципы FSD.

Полный FSD можно пересмотреть только при превращении сайта в приложение с несколькими независимыми бизнес-процессами: например, сложным калькулятором, личным кабинетом, каталогом с фильтрами, избранным или многошаговыми сценариями.

## 4. Рекомендуемая структура

```text
public/
└─ images/
   ├─ hero/
   ├─ projects/
   │  └─ <project-slug>/
   └─ testimonials/

src/
├─ app/                    # маршруты Next.js, metadata, layout, global CSS
│  ├─ layout.tsx
│  ├─ page.tsx
│  ├─ globals.css
│  ├─ not-found.tsx
│  ├─ projects/
│  │  └─ [slug]/
│  │     └─ page.tsx
│  ├─ sitemap.ts
│  ├─ robots.ts
│  └─ fonts/
├─ components/
│  ├─ layout/              # Header, Footer
│  ├─ sections/            # секции страниц
│  ├─ forms/               # ContactForm
│  ├─ motion/              # Reveal, Stagger, общие motion-настройки
│  └─ ui/                  # небольшие универсальные примитивы
├─ content/                # проекты, отзывы, навигация
├─ config/                 # данные компании и глобальная конфигурация
├─ lib/                    # небольшие сфокусированные интеграции
└─ types/                  # только типы, реально используемые в разных модулях
```

Структура является ориентиром и расширяется только под реальные страницы и компоненты. Не создавать пустые папки заранее.

## 5. Организация компонентов и данных

- Один компонент должен решать одну понятную визуальную или поведенческую задачу.
- Не выделять каждую обёртку, строку или декоративный элемент в отдельный компонент.
- Уникальная секция страницы хранится в `components/sections`.
- Повторяемая часть каркаса сайта хранится в `components/layout`.
- Универсальный небольшой элемент хранится в `components/ui` только при реальном повторном использовании или чёткой роли дизайн-примитива.
- Стили компонента хранить рядом в `<Name>.module.css`.
- Типы, используемые одним модулем, хранить рядом с ним.
- В `types` выносить только типы, используемые несколькими независимыми модулями.
- Проекты, отзывы и навигацию хранить в типизированных `.ts`-файлах, а не размазывать по JSX.
- Глобальные сведения о компании и настройки сайта хранить в `config/site.ts`.
- Локальную константу оставлять рядом с местом использования; не создавать общий файл-константосборник.

## 6. Правила React и Next.js

- Server Components использовать по умолчанию.
- Добавлять `"use client"` только при наличии состояния, обработчиков браузерных событий, browser API или Motion-анимации, требующей клиента.
- Не добавлять глобальное состояние, если данные можно передать пропсами или сохранить локально.
- Не использовать Redux, Zustand или Context как хранилище без реального общего состояния.
- Не добавлять TanStack Query или SWR при отсутствии удалённых динамических данных.
- Страницы Next.js могут использовать default export; обычные компоненты предпочтительно экспортировать именованно.
- Не создавать повсеместные barrel-файлы `index.ts`; прямые импорты упрощают поиск происхождения кода.
- Не использовать `any`. Неизвестные внешние данные начинать с `unknown` и проверять на границе.
- Не применять сложные generics, фабрики и конфигурационные DSL там, где достаточно понятных пропсов и обычного массива данных.
- Не создавать абстракцию до второго реального случая использования.

## 7. Правила CSS

- Использовать единый набор CSS-переменных для цветов бренда, контейнеров, отступов и типографики.
- Сохранять понятные имена классов по роли элемента, а не по случайному визуальному свойству.
- Не использовать inline styles, кроме действительно динамических числовых значений, необходимых React/Motion.
- Адаптивность строить от содержания, а не под перечень конкретных устройств.
- Не дублировать одинаковые медиавыражения и магические значения без необходимости.
- Проверять состояния hover, focus-visible, active и disabled.
- Не скрывать важный контент только ради визуального эффекта.

## 8. Доступность и производительность

- Использовать семантические элементы HTML и логичную иерархию заголовков.
- Все интерактивные элементы должны работать с клавиатуры.
- Фокус должен оставаться видимым.
- Поля формы должны иметь связанные label и доступные сообщения об ошибках.
- Соблюдать достаточный контраст текста и элементов управления.
- Учитывать reduced motion.
- Не загружать JavaScript для статичной разметки без необходимости.
- Не допускать layout shift из-за изображений и шрифтов.
- Не добавлять тяжёлые зависимости ради одного небольшого эффекта.

## 9. Качество кода

Использовать:

- ESLint с актуальной конфигурацией Next.js и TypeScript;
- Prettier без множества стилистических плагинов;
- проверку TypeScript;
- production build как обязательную итоговую проверку.

Предусмотреть понятные npm-скрипты для:

- lint;
- typecheck;
- format/check;
- build.

Перед завершением значимого изменения запускать как минимум lint, typecheck и build. Ошибки не подавлять без объяснимой причины.

Stylelint, Storybook, Jest/Vitest, Playwright/Cypress и полноценную тестовую инфраструктуру не добавлять автоматически. Возвращаться к ним только при появлении достаточного количества логики или критичных пользовательских сценариев.

## 10. Явно исключённые решения

Без нового требования не добавлять:

- CMS;
- базу данных;
- авторизацию;
- собственный backend;
- аналитику и мониторинг;
- CI/CD;
- Redux, Zustand и другие глобальные store;
- TanStack Query или SWR;
- Tailwind;
- Sass/SCSS;
- CSS-in-JS;
- React Hook Form;
- Zod;
- `clsx`;
- готовую UI-библиотеку;
- полный FSD;
- Atomic Design или Feature-Sliced-подобную многоуровневую архитектуру;
- GSAP;
- Storybook и тестовые фреймворки до появления обоснованной потребности.

Любая новая зависимость должна отвечать на конкретную проблему проекта. Перед добавлением проверить, нельзя ли решить задачу яснее средствами React, Next.js, TypeScript, CSS или уже установленного Motion.
