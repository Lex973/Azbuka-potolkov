# Доставка заявок: варианты решений

Дополнение к `LEAD_FORMS.md`. Там описано, что уже сделано. Здесь — чем можно закрыть главную проблему: **с VPS сайта `api.telegram.org` недоступен** (таймаут, 30.10.2026), и как ещё можно устроить приём заявок.

## Решение на 30.10.2026

### Согласованный следующий этап — отложен

Пользователь согласовал схему **постоянная очередь на существующем VPS → Telegram через Cloudflare Worker + резервная почта**, но явно попросил реализовать её **позже**. Сейчас сохраняем план; код, зависимости, сервер и правила хранения данных под него не меняем.

Порядок будущей работы:

1. Сервер проверяет заявку и надёжно сохраняет её в постоянное хранилище на VPS.
2. Только после успешного сохранения посетитель видит «Заявка принята».
3. Обработчик очереди отправляет уведомление Роману в Telegram через существующий Worker.
4. При неудаче использует резервную почту и повторяет неуспешные отправки с паузами. Состояния доставки в каждый канал сохраняются отдельно, чтобы не отправлять уже доставленное заново.
5. Доставленные и устаревшие записи удаляются по согласованному сроку хранения.

Хранилище должно переживать перезапуск и пересоздание контейнера: файл/том вне его файловой системы. Для небольшого потока предложена SQLite. При реализации явно обновить исключение из запрета базы данных в `DEVELOPMENT_RULES.md`; сейчас утверждённый стек не меняется. Резервная почта — существующий ящик Яндекса, если доступ к нему подтвердится; потребуются адрес и пароль приложения. Дополнительный VPS не нужен.

Очередь защищает принятую заявку от временной недоступности Cloudflare, но не гарантирует exactly-once: при потере подтверждения доставки возможен дубль. До реализации определить интервалы и предел повторов, срок хранения, поведение при заполненном диске, недоступности обоих каналов и перезапуске обработчика. Все изменения — сначала красные тесты, затем реализация.

### Текущая доставка

Выбран **вариант 3, Cloudflare Worker**: бесплатно, с VPS сайта Cloudflare доступен без ограничений, а Vercel перестал открываться. Код — `telegram-relay/`, развёртывание — `LEAD_FORMS.md`, раздел 6. ## Варианты

### 1. CONNECT-прокси за рубежом (альтернатива; сейчас не выбран)

Маленький зарубежный VPS (≈ 300–500 ₽/мес) с HTTPS-прокси или SSH-туннелем. На сайте задаются две переменные: `HTTPS_PROXY=https://…` и `NODE_USE_ENV_PROXY=1`.

- **Плюсы:**
  - код сайта не меняется;
  - TLS до `api.telegram.org` сквозной: прокси не видит ни токен, ни данные заявки;
  - токен остаётся только на VPS сайта.
- **Минусы:**
  - ещё один сервер, его надо оплачивать и обновлять;
  - если прокси упадёт, заявки не дойдут;
  - канал до прокси может деградировать из-за DPI. Обычный HTTP CONNECT показывает SNI, поэтому лучше HTTPS-прокси или SSH-туннель.
- **Проверить:**
  - версия Node в образе ≥ 22.21 / 24.5 (флаг `NODE_USE_ENV_PROXY`);
  - тестовая заявка после настройки.

### 2. Свой ретранслятор на Vercel

Функция на Vercel хранит токен бота и ID чата. Сайт отправляет ей готовый текст и общий секрет в заголовке, функция умеет только `sendMessage` в один чат.

- **Плюсы:**
  - Vercel доступен с сервера;
  - токена нет на VPS: при утечке секрета можно только писать в рабочий чат, но не управлять ботом;
  - нет сервера, который надо обслуживать.
- **Минусы:**
  - бесплатный тариф Hobby по условиям Vercel только для некоммерческого использования, честно нужен Pro (около $20/мес);
  - доступность Vercel из РФ может меняться;
  - ещё один зарубежный обработчик ПДн;
  - нужен небольшой отдельный код: функция-ретранслятор и второй отправитель на сайте (около 50 строк с тестами).
- **Нельзя:** делать прозрачный прокси `/bot<токен>/…`. Токен в URL попадает в логи, а прокси даёт полный доступ к боту.

### 3. Cloudflare Worker

Устроен так же, как вариант 2. Бесплатный тариф разрешает коммерческое использование, но трафик к Cloudflare из российских сетей в 2025–2026 годах деградирует. Перед выбором нужна проверка `curl` с VPS. Без неё не рекомендую.

### 4. Почта через российский сервис (Яндекс 360 / Mail.ru)

Сервер отправляет заявку письмом по SMTP. Почта домена уже на Яндексе.

- **Плюсы:**
  - работает из РФ без обходов;
  - закрывает требование локализации ПДн (ч. 5 ст. 18 152-ФЗ), Telegram его не закрывает;
  - письма хранятся, поиск по ним есть.
- **Минусы:**
  - это не Telegram: уведомление менее «живое»;
  - нужен пароль приложения для ящика и строка `ip4:168.113.168.121` в SPF (DNS у владельца);
  - одна новая зависимость (`nodemailer`).
- **Код:** заменить или дополнить `send` в `src/app/api/leads/route.ts` отправителем почты. Остальная цепочка (проверки, лимиты, дедупликация) не меняется.

### 5. Бот в MAX

Российский мессенджер, на сайте уже есть кнопка MAX, серверы в РФ. Бота может создать только верифицированная организация, ИП или самозанятый в РФ, через Госуслуги. Бот проходит модерацию до 48 рабочих часов. Токен передаётся заголовком `Authorization`, API — `platform-api.max.ru`. Источники вторичные, сверить с dev.max.ru. Решает и сеть, и локализацию. Нужен свой отправитель (около 50 строк с тестами) и аккаунт организации.

### 6. Почта как основной канал + Telegram как копия

Самый надёжный вариант: если упадёт один канал, заявка дойдёт по другому, и правовой вопрос локализации закрыт почтой. Цена — сумма вариантов 4 и 1/2.

### 7. Без своего бэкенда: внешние сервисы форм и CRM

Например, CRM с виджетом формы или сервис-конструктор. Убирает код, но добавляет стороннего обработчика ПДн, абонентскую плату и чужую разметку или скрипт на сайте. У Романа уже есть своя CRM на том же сервере (порт 3000): возможно, её API — самый естественный канал. Это стоит спросить у него.

## Рекомендация

1. Узнать у Романа, есть ли у его CRM API для приёма заявок. Если есть, это лучший вариант: данные в РФ, на своём сервере, без обходов.
2. Если нет — почта (вариант 4) как основной канал, плюс Telegram через CONNECT-прокси (вариант 1) как удобная копия.
3. Если важен только Telegram и правовой риск владелец принимает — вариант 1 или 2.
